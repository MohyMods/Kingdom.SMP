# Flexible milestones — implementation checkpoint

> D-021 changes future building reward timing: Town Hall at Tier 2, subject to separately approved save migration. Lodge/road/final-Hall references below remain existing runtime or older proposals and need review for the new profile. No resource quantities are newly approved and no executable milestone data changes in this documentation task. See CONSTRUCTION.md and BLUEPRINT_IMPLEMENTATION_PLAN.md.

Version 0.4.0-dev / protocol 5. The server reads immutable schema-1 JSON, checks the running item registry and tags, builds a prerequisite graph and publishes bounded read-only descriptions to the existing Royal Gilded progression screen. Operator validation and public inspection use actual loaded definitions. Completed Lodge objective status comes from the persistent construction project. Proposed goals are clearly disabled.

`MilestoneCatalog` defines namespaced resource/objective/capability identities, exact whole targets, categories, prerequisites, optional display text, sequential source/destination and explicit proposed approval/scoring labels. `MilestoneJson` rejects duplicate/unknown fields, malformed selectors, fractional/overflowing quantities, oversized/deep input and skipped tiers. `MilestoneValidator` checks overlapping resolved ingredients, absent items/empty tags, independently known vanilla acquisition requirements, unknown/unverified capabilities, forward gates and concrete cycles, including unused malformed dependency components. Mod registration alone never establishes an accessible approved recipe.

`MilestoneService` loads after initial tag binding and the verified NeoForge datapack-sync event on reload, swaps an immutable snapshot, invalidates old donation reviews, and guards the actual First Hearth quote/confirm before item removal. Malformed data, structural dependency failures or incompatible First Hearth definitions block **new** consumption. Existing native receipt reconciliation remains independent, so prepared old operations can settle under their original contract. No saved winner/history/score is interpreted using a changed proposal.

The existing First Hearth adapter remains deliberately pinned. This avoids an unsafe rewrite of historical arithmetic or contribution save schemas. The framework supports definitions for every tier but **does not yet supply generalized live per-tier inventory transactions, scoring version pinning, admin-road evidence approval, later winner issuance or Storehouse services**. Those need approved rules and additional native fault tests before activation. Listing all twelve rows is not the completed twelve-tier experience.

New UI design retains the established Overview/Progression/Construction shell. A selected tier shows server approval state, gathering→destination boundary, resource/category targets, objective status, reward identity and validation blockers in a scrollable parchment panel. It never offers a donation or reward button for a proposal. Existing contribution, ranking/history, Lodge/NPC and construction screens remain the active gameplay paths. Both client and server require protocol 5 because the overview now carries twelve bounded descriptions.

See MILESTONE_DATA_FORMAT.md for administration and PROGRESSIVE_RESOURCE_BALANCE.md for the **unapproved** resource/effort table. Actual execution results and screenshots are recorded in VALIDATION.md and the delivered checkpoint; do not infer runtime verification from this design alone.
